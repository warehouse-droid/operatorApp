# Stocking → Backorder conversion

Spec approval: not obtained (autonomous run). The user explicitly selected **Whole request** and **SCM**. The implementation retains the same request ID and STREQ number.

Tier 3 failure model: unauthorized conversions (real HTTP role tests); simultaneous conversion/review/TO or PO commitment (request and material locks, concurrent HTTP tests); partial writes or lost original data (transaction rollback injection and before/after snapshots); changed quantity or UOM when the item master changes (copy saved quantities and UOM, property and HTTP tests); double conversion (revision and workflow guards); old Stocking actions operating after conversion (real HTTP regression); mismatched Sales yard and material receiving yard (origin/destination access tests); UI stale saves and duplicate submissions (real Chromium); stale published modules (cache version and deployed source checks).

Acceptance criteria:

1. SCM can preview and convert an open Regular Stocking Transfer or Purchase request as a whole. Sales, dispatchers and anonymous callers cannot convert. The same request ID, STREQ number, requester, submission time, customer text and request remark survive.
2. Only an entirely open and uncommitted request can convert: 1–100 materials in submitted/changes_requested/approved state; no resolved/rejected/cancelled/fulfilled/received materials, TO lines/transfers, purchase demands, replenishment requests, SO ownership or handoff, or prior case. Reject a stale/missing/malformed expected revision. Every rejection leaves all rows and events unchanged.
3. Material identities, saved descriptions, quantities, UOM and entered pack quantities carry over exactly, using saved request values rather than recalculating against today's item master. Preserve each receiving yard and default each vendor from the regular item master; SCM can confirm/change a line's vendor in the conversion dialog. Missing vendors must be entered before confirming. Ancillary items cannot convert.
4. The Backorder inquiry store is the original requesting Sales yard (falling back to the existing destination for older requests). Material receiving yards remain independent. The original Sales yard can read/reply/edit the converted request; an unrelated Sales yard cannot. Preserve the original Stocking metadata and material rows for audit. Material rows are retired from the Stocking workflow; old Stocking events remain intact and their public history metadata appears in Backorder History.
5. Conversion captures Pickup or Delivery, a current/future required date and, for Delivery, the existing Backorder delivery address/date/window/instruction fields. It creates no NetSuite orders, local TO/PO demand, pallet link, delivery fee, sales price or sales discount. A converted request starts at new_enquiry with fresh SCM review and Sales decisions.
6. The current Backorder sequence, quote attachment at every stage, PO-link notification, manual-link business-comparison bypass, statuses and multi-select queue behavior remain unchanged. Stocking edit/review/reply/resolve/TO/proposal actions cannot mutate the converted request.
7. A locked conversion is atomic: one simultaneous caller succeeds and the other conflicts; a raced commitment cannot be lost. A failure after case/material creation rolls back all conversion writes. No duplicate request or case is created.
8. Actual Chromium displays the SCM conversion button for both Stocking types, a confirmation dialog with copied materials/vendors and fulfillment fields, safely escaped notes, Cancel without writes, busy/duplicate prevention, retained input on error, and the same request opening as Backorder after success. Sales has no conversion control. Terminal/committed requests have no active conversion control.

Setup: use only existing Node, PostgreSQL, Playwright, fast-check, c8, ESLint and TypeScript from the repository's existing test image. No dependencies, lockfile edits, git commits or production-data test access. Add task-specific tests, runner, baseline source snapshot and evidence. Preserve logs.
