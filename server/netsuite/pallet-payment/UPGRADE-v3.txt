This watches create, edit, inline edit, delete, approve, cancel and reject where
supported. Both customers are queued when a transaction is reassigned. Invoice,
deposit and deposit-application changes matter because they change funding links.
Manual pallet allocation changes also refresh balances. Generated PRA1 refund
allocation rows are ignored so the rebuild cannot trigger itself endlessly.

CSV imports must have Run Server SuiteScript and Trigger Workflows enabled.
SOAP integrations must not disable server SuiteScript triggers. NetSuite does
not chain one User Event into another User Event. If an existing User Event
creates/changes a relevant transaction, have that script call the queue library
after its successful write:

  queue.kick();
Load it as ./ppa_refresh_queue or the correct relative module path. Customer
reassignment must enqueue both customers. Do not add financial saves to the
watcher itself. Source changes made while triggers were disabled need a backfill.

Deploy it:

  Deployed: checked
  Status: Scheduled
  Log Level: Audit
  Schedule: Daily Event, repeat every 1 day
  Start Date: today
  Start Time: 12:00 am
  Repeat: every 15 minutes
  No End Date: checked
Save. It only checks and submits queued work; it does not rebuild every customer
every 15 minutes. NetSuite processor load can delay execution.

Keep the Map/Reduce writer customdeploy_ppa_rebuild at NOT SCHEDULED. The watcher
and dispatcher submit it programmatically. Do not create a second writer
deployment or put this writer on a recurring schedule at the same time.
Programmatic submissions explicitly use Queue Only=true, Preview Only=false and
blank Customer Internal ID; they are not restricted by the old 5240 test value.

Each transaction change first saves a queue entry, then attempts immediate
submission. If the writer is busy, the entry waits. The worker processes up to
50 events per run, groups them by customer and checks for more after completion.
The 15-minute dispatcher catches events arriving after that last check or a
submission failure. Rebuild failures retain their queue entries for retry after
15 minutes. A successful rebuild, including a persisted REVIEW result, removes
only the events it actually captured; newer events remain queued.

For queue visibility, create a Pallet Refresh Queue saved search with Inactive=No,
showing Name, Customer, Date Created, Retry Minute (System), Last Error. It should
normally drain after rebuilding. Repeated Last Error values indicate a source,
schema, role or governance problem to resolve; the scheduler cannot repair those.

G. Check automatic operation after installation

Use the next normal transaction save for a known pallet customer. Look for a
queue row or a PALLET REFRESH SUBMITTED / PALLET REFRESH WAITING log. Then check
the MR log for REBUILT customer <ID> and refresh the report. Its deduction should
change after a credit/refund change is reconciled. Reports are background-updated,
not recalculated synchronously on every page load. Viewing the report requires
no Save and Execute action.

If no event is captured, inspect the watcher deployment's status, audience,
execution context and permissions. PALLET REFRESH CAPTURE FAILED means the
transaction is already saved but refresh capture failed; repair it and backfill
the affected customer. If a queue row exists but does not drain, inspect its Last
Error and both the dispatcher and writer logs. The dispatcher must be Scheduled
and the single writer must be Not Scheduled.
