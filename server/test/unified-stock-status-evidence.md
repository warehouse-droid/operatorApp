# Unified Regular Stock status: implementation evidence

Implemented the shared six-status display and filters for Pickup, Delivery,
Stocking Transfer/Purchase, Backorder and Waitlist in Sales and SCM. Production
and vendor transfer remain independent waiting badges. Rejected, cancelled and
manually closed requests retain their distinct outcomes under Closed. Completed
means request work is complete; it does not universally mean physical delivery.
This is a workspace implementation; no deployment was performed.

Tier 3: additive read API and filters. **Spec approval: not obtained (autonomous
run)** for the executable expansion; the user requested implementation of the
plan. The [specification](unified-stock-status-spec.md) is available for review.
The absence of separate spec review limits confidence in whether the specification
captures every desired business rule.

## Existing failures and corrections during implementation

These nine failures occurred against both saved pre-change source and current
source during the final run. They are reported, not suppressed as new passes:

| Suite | Exact failing test names |
| --- | --- |
| Stock-request UI contracts (2) | `stock-request feedback is content-sized and availability shows Sales plus conversion equivalents`; `Sales Request Stock has complete Simplified Chinese UI and validation coverage` |
| Regular target-yard access (1) | `SQL lists and detail authorization agree across yards, methods and versions` |
| Backorder Already Ordered browser (2) | `All Already Ordered request shows Completed and no remaining SO/PO steps`; `Completing the last material after a PO was linked removes its remaining planning prompt` |
| Waitlist HTTP/browser (1) | `SCM finds an existing PO, opens its item pool, releases a mature hold and acknowledges returned stock` |
| Stocking line-action browser (3) | `SCM Purchase actions send only the clicked material even when other materials are pending`; `Transfer Stocking reply and Resolve controls belong to the individual material`; `Sales can reply only in the instructed material card and sends its line ID` |

The corresponding `baseline-*.log` files and current suite logs are retained in
the artifact directory. Two UI contracts already disagreed with grid styling and
script-query ordering; Backorder browser expectations already disagreed with the
conversation forms. The baseline comparison does not establish that these older
behaviors are correct, especially the remaining yard-access discrepancy.

Historical RED evidence is separate from final results: the initial model stub
failed all 18 then-existing example/property tests in
[red.log](../test-artifacts/unified-stock-status/red.log); the first SQL/HTTP/browser
run failed all 5 then-existing cases in
[integration-integration-red.log](../test-artifacts/unified-stock-status/integration-integration-red.log).
Subsequent assertions exposed compact/full Waitlist disagreement, a missing SCM
case-stage intersection, toolbar overflow, stale Resolve drafts and deep links
outside the first 100 records. Those implementations were corrected. The
ignore-supply-filter mutant also exposed a missing negative example, which was
added before repeating the mutation checks.

The existing Resolve tests now use the status selector and explicitly select
Completed before inspecting finished work. Their required-field, no-extra-submit,
persisted-data and draft-discard assertions remain. Test fixture/browser setup was
also corrected: standard cached headless Chromium avoids the read-only-container
crashpad issue. Repeated instrumented navigation caused a renderer crash; the
deep-link scenario now uses a fresh page in the same authenticated context while
retaining language, viewport and persisted-preference assertions. Memory counters
did not establish an OOM cause. Coverage is captured before navigation so earlier
page execution is retained.

## Limits and host cleanup

The full repository includes unrelated applications and workflows; only the
selected affected unit/property and integration suites ran. Whole-application
typing, a separate formatting tool, accessibility auditing, alternate browser
engines, a production-scale latency benchmark and concurrent-update stress tests
were not run. Small shared helpers separate classification, rendering and query
pagination; complexity was reviewed structurally without a numeric analyzer.
No latency budget was specified. Filtering complete records in batches of 100
can increase read cost for large histories; that cost is not quantified here.

The repeat stage passes reversed file arguments, but Node normalizes their order.
It establishes repeatability, **not randomized-order coverage**. Dependency and
license audits were not run because this task added no dependencies. No live
NetSuite writes were exercised. No migration or rollback rehearsal was required
because no schema migration was introduced. Branch coverage is below 100%; the
coverage figures do not prove every possible business input is handled.

Teardown was registered before starting containers. The runner used
`mbbs-tests.slice`, bounded memory/CPU/PIDs/tmpfs and `--rm`, then
`docker compose down --volumes --remove-orphans`. Both final
[running-container](../test-artifacts/unified-stock-status/docker-running-full.log)
and [all-container](../test-artifacts/unified-stock-status/docker-all-full.log)
inventories contain only the four production allowlisted containers. The test
project's volume and network inventories are empty. Application, database and
Ollama health checks were healthy, the webhook worker was running, and the
application `/health` response was HTTP 200. Logs and screenshots were preserved;
test databases and containers were removed.
