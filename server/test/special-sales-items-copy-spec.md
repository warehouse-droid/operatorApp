# Special Request: add items and copy

Spec approval: not obtained (autonomous run). Tier 3: request data, public API, concurrency.

1. Sales sees a purple **Add item** button after all Case lines and before Close case on an active request without an SO/PO or order submission. Pressing it opens a centered custom warning: adding items returns the request to New enquiry; it is allowed only before creating a Sales Order. Cancel/Escape saves nothing.
2. Continue opens an editor for new items only. Submitting one or more valid items appends sequential lines and returns the existing request to `new_enquiry`. Every column of each existing item, including name, price, discounts, stock response, availability, and customer decision, remains unchanged. Existing unsent SO draft lines are invalidated so they cannot omit the new items.
3. A revision conflict, an unauthorized yard, a closed/closing/completed request, a linked or test-skipped order, a creating/uncertain/submitted remote operation, and a pending quantity/fulfillment review each reject the update with no inserted items, changed old lines, revision bump, or success event. Concurrent appends allow only one commit per revision; an order claim racing an append cannot create an incomplete order.
4. Added lines use the same validation as a new request (supported UOM, positive finite quantity, finite nonnegative rate, bounded discount/packs, real date today or later, required product). Combined count cannot exceed 100. Malformed or hostile batches fail atomically. All lines belong to the existing vendor.
5. **Copy the request** appears beside the SPREQ label, including closed/completed requests. It opens an editable new-request draft containing all item descriptions/specs, quantities/UOM, rates/discounts/packs/notes, vendor, customer and phone, inquiry yard, delivery method/address/contact/window/instructions, Sales Rep and case remarks. Inquiry and expiry dates are fresh for the new request; other copied dates remain visible for review. Old request IDs, stock responses, order links, and closure state do not become new-request state.
6. Copy and editing its draft make no request-creation POST. Only an explicit **Submit to SCM** creates the new request. Cancel leaves the source unchanged. Selecting a different request cannot carry new-item edits to it; failed submissions retain entered values. Phone layouts remain usable.
7. Existing PALLET creation, real PO Note updates, local PO Split Remark/Note, two-row special mini panel, Ready for Arrangement wording, item description formatting and PO/TO schedule changes remain deployed.

Failure model: lost old-line data (full SQL-row comparison); partial append (real PostgreSQL failure injection/rollback); stale/concurrent SO or append (shared row-lock races and HTTP revision checks); unauthorized edits (real authenticated HTTP role/yard/feature checks); hostile input/overflow/unbounded batches (negative examples and deterministic fast-check properties); accidental copy creation (browser request interception and unchanged-source assertion); stale draft causing incomplete SO (draft deletion and real order-claim rejection); XSS (escaped browser rendering).

Setup: reuse the existing isolated Node/PostgreSQL/Playwright runner and installed TypeScript, ESLint, c8 and fast-check. Add scoped tests, a reproducible check command, deployment overlay and evidence report. No dependency changes, package installs, commits, migrations or test writes to live NetSuite. Capture the current live source, deploy only reviewed feature files over that image, keep worker/database/Ollama and container configuration unchanged, verify health and exact public asset hashes.

Clarification from the existing policy: disabled Special Request workflows return HTTP 404 (`SPECIAL_STOCK_DISABLED`), not 409. The new route must preserve that established gate response. The acceptance assertion uses 404; all state-lock rejections still require 409.

First GREEN run: linked-order rejection fixtures must supply the order reference as required by the existing database constraint. The property generator retains quantity/rate extremes and explicitly expects `SPECIAL_SUBTOTAL_INVALID` when their exact subtotal in cents exceeds `Number.MAX_SAFE_INTEGER`, matching existing monetary validation. These correct fixture assumptions; rejection and data-preservation assertions remain required.

The test-only PO-skip fixture also includes the required prior SO skip, preserving the database's existing skip constraint. If another session creates the SO while Sales is adding items, a rejected submission must leave a visible, disabled editor containing the entered items and an available Cancel button; the user must not be stranded by a hidden draft that blocks refresh.

Additional adversarial/compatibility fixtures retain the existing privacy and pricing contracts: Sales responses omit purchase costs (the database must still keep new costs null), and an existing PALLET price cannot be edited. The post-SO compatibility scenario adds the first PALLET to an SO that had none; only this state exposes the initial price input. The first run caught these fixture assumptions; assertions now explicitly preserve both contracts rather than changing the app to satisfy them.
