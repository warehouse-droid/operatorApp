Special Order case-line field parity — Tier 3

Spec approval: not obtained (autonomous run). The user's request authorizes adding all New Request line fields to the existing Sales editor.

Acceptance criteria:

1. Edit case lines shows the same editable fields and layout as New Request: product name, colour, size, Detail Spec, quantity, Sales UOM, sales rate, discount, required date, line note, PLT, LYR, SEC and PCS. Saved values prefill correctly, including zero values and legacy units/dates. Inputs survive re-render, decline/revoke, validation errors and revision conflicts. Cancel writes nothing.
2. Saving any changed field persists it on the same line. Product name, quantity, colour, size, Detail Spec, UOM, required date and packing changes require the existing restart confirmation and reset only changed material reviews. Both unsent order drafts are invalidated. Unchanged lines and private SCM review evidence remain protected.
3. Discount-only and line-note-only edits preserve the existing stage/reviews/decisions. Discounts update the current and quoted discount, quote subtotal and saved unsent SO native discount (or converted legacy rate), preserving purchase costs and unit conversion. Line notes do not recalculate draft prices. Combined rate/discount edits use the new values together.
4. Missing added fields in older API payloads preserve saved data. Equal normalized values are no-ops. Existing historical required dates and legacy UOMs are retained when unchanged; newly selected dates must be today or later in Toronto and new UOMs must be one of New Request's six units. Optional text and packing can be cleared.
5. Reject invalid dates, unsupported UOMs, hostile types, oversized/control-character text, discounts outside 0–100 or beyond four decimals, negative/nonfinite/oversized packing, bad IDs and unsafe quote totals. No partial writes, private-field injection or external service calls.
6. Preserve existing Sales/yard/revision/active-request checks and pre-order limits, decline/revoke behavior, PALLET and delivery-fee editing. Concurrent writes serialize; SQL failures roll back the entire edit. A scoped migration permits rate basis and quoted discount edits only within the existing transaction-local pre-order editor guard; out-of-editor and issued-order changes remain denied. Repeated migration and rollback are verified without rewriting request rows.
7. Verify real browser interactions at desktop and phone widths, actual HTTP/database persistence, quote rendering and saved draft pricing. Publish only this task's changes over the captured live image, preserving other services/configuration and keeping a rollback image.

Failure model and checks: missing/misbound form fields (browser payload and reload assertions); stale reviews/conversions (real SQL reset/preserve tests); wrong or doubled discount (native and legacy draft and quote assertions plus generated properties); coercion/overflow (adversarial input tests); partial updates/revision races (existing HTTP rollback/concurrency suite); unsafe price trigger (migration scope/lock/rollback tests); unrelated deployment changes (source hashes and guarded live overlay).

Setup: use a temporary isolated source copy, installed Node, TypeScript, ESLint, c8, fast-check and Chromium in the existing test runner, and its isolated PostgreSQL database. No new dependencies or Git commits. Add focused tests, this spec, reproducible check/release scripts and an evidence report. Baseline failures will be recorded and held to zero new failures. No production business-record writes or NetSuite writes are needed for verification.

User scope addition: SCM stock-check corrections.

8. During the existing pre-order stock check, SCM can correct product name, colour, size, Detail Spec, quantity, UOM, PLT, LYR, SEC and PCS. Saved fields prefill and submit through both single and batch stock-response paths. Omitted fields preserve existing values. Use the same bounded field validation as Sales, without granting SCM access to selling rates, discounts, required dates or customer notes through this correction payload.
9. SCM corrections save with the stock response atomically and appear in Sales' request and quote. A material correction clears old item resolution/conversion and customer acceptance, invalidates unsent SO/PO drafts, and retains the newly entered stock check for customer confirmation. Unchanged lines and selling rates/discounts remain intact. Correction audits are visible to Sales/SCM without private cost data. Existing post-order/readiness, request/operation and revision locks remain enforced.

User scope addition: Request order adjustment after SO creation.

10. The existing Sales adjustment form includes the same material fields (original sales rate remains fixed under the existing order policy). Every proposed field appears in SCM's review. Required date and line note remain request metadata, as in New Request. Pending proposals do not alter saved lines or remote orders. Rejection preserves original data; approval applies the saved proposal only after both issued orders verify successfully.
11. Description corrections update the issued SO/PO description, packing corrections update their existing custom PLT/LYR/SEC/PCS fields, and UOM corrections use an explicit pieces-per-sales-unit conversion to update quantities and prices consistently. Existing remote PC/native units, linked line identities, purchase unit costs, unrelated fields and original selling rate remain protected. The original UOM basis can change only for the line/UOM in an applying SCM-approved adjustment. Changes cannot bypass Dispatch, fulfillment, revision or retry guards.
12. Extend durable adjustment snapshots to validate descriptions/packing and retries. Unreviewed remote edits block writes; partial SO/PO failures can resume without duplicate changes. Existing metadata-free adjustment plans remain compatible. Validate new HTTP proposal/approval/rejection and adapter boundary cases along with existing adjustment/recovery suites. No real NetSuite write is needed for testing.

Coverage-driven behavior audit: pending Sales and SCM reviews must show every proposed field and the changed conversion as escaped text, without submitting a write. Browser assertions cover this review boundary; a deliberate omission fault must make them fail. Multiline saved details/notes must remain byte-for-byte unchanged during a price-only edit.
