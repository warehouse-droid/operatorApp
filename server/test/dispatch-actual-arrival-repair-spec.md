Acceptance scenarios, written before implementation:

1. A completed pickup followed immediately by an automatically started delivery has server-created destination verification coordinates in a separate record. Reconstruction reads matching evidence and derives the delivery arrival from Samsara history. The preceding travel leg ends at that arrival, not at job start.
2. Coordinate evidence must belong to the same driver and recorded job, precede completion, match the recorded destination, and contain finite, geographically valid coordinates. Wrong-driver, changed-address, future, blank, invalid and current-truck-position evidence cannot supply a destination. Existing direct expected-coordinate evidence and configured yards remain supported. No new Google requests are introduced.
3. Same-site visits can use the previous completion without requiring coordinates when their recorded physical address establishes the same site. The first physical visit keeps its original PWA start by the existing policy.
4. A sustained GPS cluster continuing across the initial history-window boundary must search earlier history and retain the true observed cluster start. The existing dwell/radius requirements remain intact; missing or sparse GPS stays unresolved with an accurate reason.
5. A retained unresolved calculation must not display the next job's start as actual arrival in the forecast, compact cards, grouped cards, preview, or timing details. Actual completion remains visible. UI communicates that arrival is unavailable. Existing resolved arrivals remain authoritative if a new calculation is unresolved; first-stop/legacy behavior without a retained failure is preserved.
6. Historical application updates only the canonical derived arrivals and calculation/audit records. Original driver starts, completions, photos, job details, plans, and source orders remain unchanged. All logical records of a physical visit receive one arrival. Stale previews are rejected, and repeated apply is idempotent.
7. All completed historical driver-days through the captured cutoff are attempted, without truncating the earliest dates. Each route is previewed and applied through the existing guarded repository path. The resumable backfill records exact route/run IDs, totals, failures, and unresolved reasons, and preserves pre-existing resolved arrivals when no replacement is supported.
8. The release contains only this repair over the deployed image, retains service configuration and unrelated services, is health-checked, and has a rollback image. Live before/after fingerprints verify that original operational evidence was not rewritten. Pending unrelated workspace changes are preserved.
