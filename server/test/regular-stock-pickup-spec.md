# Pickup requests: SCM review and direct TO conversion

User requirements: every pickup request needs SCM review, SCM can adjust quantities and add items through autocomplete before converting directly to real TOs. User explicitly confirmed that Sales does not enter an SO or confirm routing for pickup, and authorized deployment after tests pass. Delivery retains its SO approval/routing workflow. Completed prior requests remain historical snapshots.

Tier 3; spec approval not obtained (autonomous run), behavior and deployment explicitly authorized. Continue the old-coder workflow, existing pinned Docker toolchain, fresh isolated database, no dependencies or commits. Capture the currently deployed sources, test a scoped overlay, preserve runtime configuration and worker.

1. Pickup never auto-approves, regardless of gate, stock or lead time. Submission, edits and re-raising explain `Pickup requires SCM review and direct TO conversion`. Delivery retains gate/safety/lead conjunction.
2. SCM opens a centered TO editor containing all undecided/approved pickup lines, excluding rejected/cancelled ones. Quantity/source changes and autocomplete additions remain a draft until confirmation. Original item identity cannot be swapped silently. Positive quantities, conversion units, 100-line limit, valid distinct source/destination and current revision are enforced server-side.
3. Preview refreshes inventory, displays final quantities/routes/safety and requires explicit confirmation. SCM supplies/accepts PALLET quantity for each route. Cancel creates nothing. Confirmation of a changed payload or request fails before any order write. Unauthorized roles cannot search/preview/convert through SCM endpoints.
4. Confirmation records line changes and the SCM approval snapshot atomically, creates one local transfer per source/destination, then issues the real TOs using existing marker/external-ID recovery. No SO ownership, location change or SO dependency is created. Rejected lines remain rejected. Audit retains before/after and Sales receives a manual approval notification.
5. Duplicate/concurrent confirmation cannot issue additional TOs. If one route fails after another succeeds, the stored conversion resumes the same transfers without accepting quantity/item edits or re-creating successful orders. A printer failure after a committed/hydrated TO does not create a duplicate. Execution-disabled and invalid drafts fail before claiming work.
6. Pickup uses an SCM conversion/retry state rather than Sales SO entry or its approval-expiry countdown. New Sales SO attempts for unclaimed pickup are refused server-side; already-claimed older SO work can recover. Existing completed pickup SO snapshots stay readable.
7. Sales and SCM can reopen the issued TO references, adjusted quantities and saved decision snapshot. All buttons stay disabled during NetSuite waits, including the editor; error recovery unlocks the correct controls. Delivery behavior, exact SO quantities, non-stock companions, expiry/re-raise, SO uniqueness and old transfer workflows remain covered.

Failure model: bypass pickup gate (property tests), stale/hostile draft (domain/SQL/HTTP tests), unauthorized conversion (HTTP roles), partial transaction mutation (rollback assertions), duplicate/partially committed TOs (concurrency/retry integration), edited UI lost on autocomplete/refresh (browser), accidental migration of completed history (live read-only check), unrelated workspace deployment (baseline/image tree hashes). Live validation will not create or edit user orders; NetSuite writes are tested at the boundary in an isolated environment.
