Spec approval: not obtained (autonomous run). Tier 2. The user requests refreshing all routes and mappings in the selected date plan when Confirm is clicked, ensuring Google estimates are attempted for every route, and saving the latest versions in the database. The user explicitly chose confirmation with a warning, retaining available estimates when Google fails. Background queuing was requested only if simultaneous requests cause failures; production evidence shows the existing requests are sequential and all recorded Google calls succeeded.

Acceptance:
- Confirm traverses every editable route with physical travel in the date plan, including routes whose saved/cached Google estimate is currently valid. Fresh confirmation bypasses the browser estimate cache. Rendering, draft autosave and load selection do not call Google.
- Process routes once in driver load order, including truck switches. Recompute each route's actual departure and signature after the preceding estimate updates its finish time. A same-route manual request already in flight can be awaited rather than reported as a failed or duplicate refresh.
- Date/plan/route changes during a request prevent stale timing and mapping from being applied or saved. Empty, single-stop and zero-travel loads require no Google trip; shared BIN loads retain their existing ownership restrictions.
- New valid Google timings, road paths, ordered stop coordinates, route identity and estimate timestamp are serialized before final confirmation and survive save, confirmation, compact updates and database reload. Invalid or stale estimates remain rejected by existing serialization rules.
- Google denial, timeout, provider error, invalid legs or absent mapping are reported by route after successful confirmation. Keep a previous usable matching estimate when refresh fails. Continue ordinary saving and confirmation, as the user chose; no timed paid retry is added. Retain central budgets, standard-route waypoint policy and manual-refresh controls.
