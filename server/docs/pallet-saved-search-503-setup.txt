Why use a RESTlet for the report
  Native REST can execute saved searches at:
    GET /services/rest/query/v1/savedsearch/customsearch503/result
  This account's endpoint returned HTTP 500 UNEXPECTED_ERROR during investigation,
  for both script/internal IDs and synchronous/asynchronous requests. Listing the
  search succeeded. The deployed RESTlet subsequently returned the actual schema.
  Native REST also cannot override saved-search criteria.
  The supplied SuiteScript loads the original saved search with N/search, adds a
  customer filter in memory, and runs it. It never calls save() or writes records.

NetSuite setup
  1. Upload server/netsuite-pallet-balance-search-restlet.js to the File Cabinet's
     SuiteScripts folder. Create a RESTlet script record using that file.
  2. Create a deployment for the integration role/user. Test it under that role,
     then release it for the intended integration audience. The role needs access
     to customsearch503 and the transactions/customers used by the report.
     Use the account-specific External URL displayed on the deployment.
  3. Use OAuth 2.0 with the RESTlets scope enabled on the integration and included
     in its token grant. Reuse existing credentials only if they support this
     scope; do not reset existing integration credentials. A Web Services Only
     role cannot call RESTlets. Match the report user's relevant subsidiary and
     location access when comparing results.
  4. Make an authenticated GET request to the deployment External URL, appending:
       &customerId=5240
     Headers:
       Authorization: Bearer <OAuth 2.0 access token with restlets scope>
       Accept: application/json
       Content-Type: application/json
     Keep authentication in the backend, never in the operator browser.

Response contract
  savedSearchId: customsearch503
  customerId: "5240"
  generatedAt: time the RESTlet ran
  found/rowCount: whether/how many rows the report returned
  columns: ordered index, name, label, join, summary, formula and sort metadata
  rows: ordered arrays of raw values corresponding to columns

  The verified balance column is quantity, label "Returnable Quantity",
  summary SUM, empty join and formula. It is index 2 in the current response.
  The adapter locates it by column identity, so column order is not assumed.
  The other columns are entity GROUP, mainline GROUP (twice), and
  phone GROUP with join customerMain. The complete grouping is validated.
  Verified results: customer 5240 = 13 and customer 1959 = 2.
  The script does not guess a column name or add numeric columns together.
  Repeated formula column names remain distinct.

  Verify the row grouping, units, saved location/date/item criteria, summary
  filters and role visibility against the UI report before selecting a column.
  Temporary UI filters are not automatically saved-search criteria.
  No extra yard-150 filter is added: the search's saved criteria remain intact.
  If there are multiple rows, determine their grouping before choosing a total.
  A structurally valid missing row grants zero allowance and retains
  balanceFound=false. Search/permission errors propagate as errors.
  More than 50 customer rows fail rather than truncate in the RESTlet;
  the app requires at most one customer result row.
  Pin the chosen column's name/join/summary/formula and expected grouping in the
  backend adapter; reject changes instead of silently reading another column.

OperatorApp integration
  A. For account 6518947, config.netsuite.palletBalanceRestletUrl defaults to
     the verified deployment above. NETSUITE_PALLET_BALANCE_RESTLET_URL can
     override it; an explicit empty value disables the saved-search mode.
     Other accounts have no default. URL validation requires the configured
     account's HTTPS RESTlet domain and path before requesting a token.
  B. Use the numeric report net balance as the NetSuite base amount:
       operator available = max(saved search net balance
                                - local returns not yet reflected in NetSuite, 0)
     The response includes netBalance, source="netsuite_saved_search",
     savedSearchId="customsearch503", balanceFound and lookedUpAt.
     fulfilled and netsuiteReturned are null in this mode because the report
     does not provide those separate totals. The operator uses available.
  C. Retain the existing credit-memo ID/external-ID and linked-credit queries.
     They identify which local returns are already included in NetSuite, so
     those returns are not subtracted twice. A summary report alone does not
     necessarily provide this transaction identity evidence.
     Skip the identity query when no local pallet returns exist. Otherwise
     read identities BEFORE the report, retaining conservative reservations
     if a credit is posted between the two reads.
  D. Keep existing local reservation, customer locking, duplicate-return and
     freshness checks. Recheck the NetSuite amount on submission. Never treat
     an unavailable/ambiguous report or a stale cache as fresh return entitlement.
     Enquiries and submissions fetch fresh reports. Report errors never trigger
     a silent fallback to the historical transaction calculation.

Operational limitations
  Saved-search criteria and role access define the balance. No extra receiving-
  yard filter is added. The current RESTlet returns a summary, not the individual
  transactions included. Keep its intended credit, date, item and location scope
  compatible with the credit-evidence rules before editing report criteria.
  Schema or grouping changes fail explicitly until the adapter is reviewed.
  NetSuite latency varies; see live-before.json/live-after.json in the release
  directory for measured timings, rather than assuming this source is faster.
  The post-deployment sample returned 13 for 800909 and 2 for 800809, with zero
  local reservations. Warm median lookup was 1.395 seconds versus 0.586 seconds
  before switching. This change aligns the source with the report; it did not
  improve lookup latency in the measured sample.
